# Spine-Runtime 项目

厂商针对智算核给出的编程模型，也是唯一有文档的提交入口。`libspert` 是预编译的；
API 与调度模型是公开的。

## 固定来源

| 字段 | 取值 |
|---|---|
| 上游 | `https://github.com/spacemit-com/spine-runtime.git` |
| ref | `main` |
| 提交 | `b3ff5182de116613b6db72b0f43064554ac3d42d` |
| 许可证 | MIT |
| 检出 | `src/spine-runtime` |
| SDK 包 | `spine-runtime.riscv64.0.6.2.tar.gz`，`libspert.so.0.6.2` |

模型是 Tile-SPMD：`Stream` 持有后端授予的计算核，`Grid` 把工作切成 tile，每个 tile
从 `Context` 读取自己的坐标。`backend_info()` 报告实际获得的核心数、共享缓冲大小、
向量长度与架构 id。`spacemit-k3` 后端面向智算核 8-15，每核 384 KiB 缓冲；
`spacemit-k3-x100` 是 X100 核上的兼容模式，`generic/qemu` 仅供功能验证。

## 状态

- 文档仓库与 SDK 身份已同步；SDK 作为密封输入留在 Git 之外，其摘要写在
  `sources.lock.yaml` 中。
- 板上尚未安装 `spacemit-runtime`，因此第一个 A100 程序仍需该包或预编译 SDK。
- 自动化已就位：`scripts/build.sh` 用 SDK 与板卡的 `spine_tcm` 头文件交叉编译
  `src/spine_runtime_project/a100_probe.cc`，`scripts/run.sh` 负责交付、执行并把输出留作证据。
- 板上实测：默认后端报告 `arch_id 0xa064`（A100）并授予 8 个核（id 8-15）；900000 次
  启动的窗口以厂商侧为证据——运行时对这批工作的注册、授予提交方 pid 的 TCM 块——再加上
  该内核自身尺寸与启动次数所蕴含的吞吐算术。逐 CPU 计数器与 `/proc/stat` 会被记录，
  但在此板上不是 A100 证据：2026-09-18 实测智算核的工作不会推动它们。

## A100 ISA 标志与我们提交的内核

`scripts/build.sh` 为智算簇编译这两个二进制（它们的内核在簇上执行）：默认是
`-march=rv64imafdcv_zicsr_zifencei_zba_zbb_zbs_xsmtvdotii -mtune=spacemit-a100`，
即显式给出 A100 ISA 与厂商调度模型，而不用那把"打包式"的 `-mcpu` 开关。可用
`SPERT_A100_FLAGS` 覆盖。

选定它的矩阵如下，每个构建跑 5 次 `a100_bandwidth 64`（每次含 4 个变体，只有 4 个都
完成才计为成功一次）：

| 构建 | 完成次数 |
|---|---|
| 纯 `rv64gc` | 4/5 |
| 只用 `-mtune=spacemit-a100` | 3/5 |
| `-march` 不带向量 | 3/5 |
| `-march` 带向量 | 4/5 |
| `-march` 带向量与 `_xsmtvdotii` | 3/5 |
| `-mcpu=spacemit-a100` | **0/5** |

两个发现，以及一处对本文件早先说法的更正。更正：该项第一次测量（3 次）写成"这个标志
决定它们能否运行"；做到 5 次后真相更窄——只有打包式的 `-mcpu=spacemit-a100` 是确定性
失败，其余任何子集的表现都与纯构建无异。这也意味着工具**本身就在随机失败**：连纯构建
也大约五次里失败一次，这是工具或它对运行时的用法里的未解缺陷，而不是任何 ISA 选项的
问题，也正是默认值现在避开那把每次都失败的开关的原因。

内存天花板不受这些影响：纯构建与向量构建在纯流式上一致为 24.6 GiB/s，在解码路径自己
那条瓦片走法上接近 23 GiB/s，因此天花板是总线而不是指令组合。标量半字节解包在所有
构建里都读 2.7 GiB/s；要回答 4 bit 格式本身能否喂满总线，仍需手写向量化解包。

## 一次读取服务 R 行

`a100_bandwidth` 现在还带有 `gemvR1`、`gemvR4`、`gemvR8`：对打包的 4 bit 权重走一遍，
分别服务 1、4、8 行激活，每个结果都与主机侧参照比对。在 1.5 GiB 工作集下实测：

| 变体 | MiB/s |
|---|---|
| `gemvR1` | 2,610 |
| `gemvR4` | 2,481 |
| `gemvR8` | 2,547 |

速率随 R 增长保持不变，而厂商自己的内核会掉速：解码运行中它的单行 `i8i4` 内核流式
9.0 GiB/s、四行内核 5.8 GiB/s。这正是本仓库能为 LLM 那条线回答的问题形状——批处理因
重新分组而损失的 25 % 至 30 % 是厂商内核结构的属性，而不是内存路径的属性——前提是
说清本内核是标量的：它只证明 R 不改变*它自己*的速率，并不证明它达到了厂商的速率。
向量化解包版本是下一步，而现在的构建已经能接受可运行的 A100 ISA。

## 不要让编译器去向量化这些内核

想用 `-O3 -mrvv-vector-bits=zvl` 走捷径，结果是**每个变体都算错**，包括最简单的
`word` 与 `byte` 循环——只因为每个变体都要与主机侧参照比对才被发现。`zvl` 会从
`-march` 字符串取向量长度，而厂商扩展集带着 `zvl1024b`，智算核实际是 `vlen=128`，
于是编译器面向一台并不存在的机器生成代码；GCC 15 只接受 `scalable` 或 `zvl`，
因此也无法直接写 128。这个构建也没有更快：`word` 从
24,759 掉到 9,741 MiB/s。回答那个问题只剩手写内核一条路，而且它必须自带校验和。

## 手写内核同样达不到厂商的速率

解包部分的手写内核现在有了（`pack4v`，RVV 内建函数，带主机侧校验），它把问题回答到了
另一边：

| 变体 | MiB/s |
|---|---|
| `word`（纯流式） | 24,168 |
| `tiled` | 23,233 |
| `pack4`（标量解包） | 2,728 |
| `pack4v`（RVV 解包） | 2,536 |

向量解包**比标量循环还慢**，而两者都低于厂商单行内核（9.0 GiB/s）3.3 至 3.6 倍。厂商的
优势几乎可以确定来自 IME2 指令族：工具链能生成它，但本工作区没有它的编程模型文档。
因此结构性的发现——批处理损失的 25 % 至 30 % 源于厂商内核结构而非内存路径——依然成立，
但要把这笔收益兑现，需要 IME2 文档，而不是在这里继续测量。另有两条旁证记录在案：逐通道
归约的版本更快但结果错误（失配量恰好等于一个 pass 的半字节和），以及工具现在在失配时
同时打印期望值与实际值，而不只是 "mismatch"。

## IME 文档是存在的，而且这些指令在 X100 核上可运行

上面那段写在查阅规范之前。规范确实存在——`spacemit-com/riscv-ime-extension-spec`
公布了指令（`vmadot`、`vmadot1`/`2`/`3`/`n`、`vmadotu`/`su`/`us`，以及浮点的
`vfmadot*` 族）、数据类型（int4/int8/int16、fp4/fp8/fp16/bf16）、由 `vl*SEW` 决定的
MAC 单元，以及编程模型（复用 RVV 寄存器、不新增状态、VLEN 128–4096、SEW 4/8/16、
LMUL ≤ 1）——其 `example/vmadot-gemm-demo.c` 是一个自带自检的 4x8x4 int8 GEMM。

本地实测：该示例用 `-march=rv64gcv_xsmtvdotii` 编译（纯 `-march=rv64gcv` 会拒绝该
助记符），在 **X100 核**上运行并打印 `Test successful. CRef equal to C.`，`taskset -c 0`
同样通过。同形状的循环实测：标量 786 Mmac/s，`vmadot` 18,286 Mmac/s——23 倍——但
**结果不同**，因为 VLEN=128、SEW=8 时 MAC 单元是 2x2x4[x2]，操作数必须按示例里
`Gemm_packB` 的方式打包。

所以“IME2 无文档、只能经智算簇运行时到达”这句话对本板不成立：指令集是公开的，并且作为
普通用户态代码在 Linux 簇上执行。自己写多行内核这件事重新开放，前提是先写好打包例程并
通过自检。

## 这样的内核实测到多少

用 demo 的形状、B 操作数只打包一次，然后从大缓冲里流式读取，累加器在整个循环里常驻向量
寄存器；**单个** X100 核、`taskset -c 0`：

| 权重缓冲 | 校验 | 速率 |
|---|---|---|
| 256 MiB | ok | 8,029 MiB/s |
| 1 GiB | ok | 7,832 MiB/s |

与其他流式实现对比：我们的标量解包在全部八个智算核上是 2.7 GiB/s、RVV 解包 2.5 GiB/s，
厂商的单行内核在智算簇上每内核 9.0 GiB/s。也就是说单个 X100 核已达厂商单内核速率的
15 % 以内；八个这样的核将索取约 61 GiB/s，而天花板是 24.6 GiB/s；MAC 单元本身就是
"每个权重块配一个四行激活块"（正是厂商在重组批时丢掉 25 % 至 30 % 的那个结构）；而且
这一切都是 cpu0-7 上的普通线程，`taskset`、按进程记账、perf 与 eBPF 采集器全都适用。

另有一条记录：X100 核上 `csrr vlenb` 读出 32 字节，即 **VLEN=256**，而智算簇后端报告
128——两簇不可互换，这也是为 VLEN=256 编写的 demo 能在本板通过的原因。

尚未完成：多核版本、解码形状的 K，以及任何端到端 token 速率。

## A100 需要自己的布局工作，而且这部分靠测而不是靠读

解码工作跑在智算簇上，所以真正要紧的是 A100 的内核——而 A100 的 **VLEN=128**、X100
是 256。规范里的 `Copies` 规则让这个差别成为结构性的：
`Copies = (sqrt(VLEN/64) is an integer) ? 1 : 2`，于是 VLEN=128 得 Copies=2、
VLEN=256 得 Copies=1，随之而来的操作数布局也不同
（VLEN=128、SEW=8 选 2x2x4 MAC 单元；VLEN=256 则是 4x4x8）。

两条结论按“记录而非假设”处理：本板验证正确的厂商 demo 是 **VLEN=256** 内核，其布局
不能直接搬用；只按规范文字写出的内核——A 为 `Copies*(M,K)` 行主序、B 为 `Copies*(K,N)`
列主序、每条 `vmadot` 出 2x2 输出且 K=8——能在 A100 上编译运行，但**复现不了参照**
（四个输出全部不符）。规范的布局图是图片，其整数伪代码又把 C 当作 (M,N) 矩阵却索引
`i*K + j`，在 M ≠ N 时不可能成立。

出路是用一个布局探针把置换关系**测出来**：通过 `spert` 提交到 8-15 核，与本工作区当初
测“tracepoint 程序按 tracepoint 挂载而非按 CPU”是同一方法——源码是假设，探针是事实。
随后是打包例程，然后是 R=1/2/4 下相对厂商 9.0 与 5.8 GiB/s 的速率。

### 在启动在飞时异常退出会把运行时一起带走

该探针的两次尝试都落在同一处：

| 事件 | 症状 | 恢复方式 |
|---|---|---|
| 探针运行中被 `pkill` | 之后所有 stream 被拒（`reason=stream-refused`），`a100_probe` 无输出，TCM 8/8 空闲 | 重启 |
| 探针段错误 | 同样症状，连刚才能正常工作的 `a100_bandwidth 64` 也返回零结果 | 重启 |

重启后簇立刻恢复健康（`a100_probe` 报 `kernels=ok mismatches=0 us_per_launch=31.2`，
`a100_bandwidth 64` 报 `word 24,881 MiB/s`），因此被破坏的是运行时侧状态而非硬件。由此
得到适用于本工作区所有 harness 的规则：不要 kill 正在提交启动的进程；提交方段错误要同等
对待；任何异常退出之后，都要先重新确认簇健康再相信下一次测量。探针本身分三个阶段尚未
完成：先是空转（八核 stream 上用单 tile 网格、且没检查 `future.valid()`）；随后段错误
且诊断信息被 stdout 缓冲吞掉；再到后来改成无缓冲 stderr + 单次启动跑完 32 个用例，仍在
sync 处段错误——但输出把故障定位到 launch/sync 边界，而且**这次没有污染运行时**
（紧接着 `a100_probe` 与 `a100_bandwidth` 都正常）。因此“段错误会毒化运行时”的说法
收窄为：kill 两次都毒化了，段错误毒化过一次；可靠规则是不要在启动在飞时 kill，并且任何
异常退出之后都先核对簇健康、而不是假定结果。

与这里所有能工作的内核相比，本探针有两处不同，直接指向下一步实验：它执行 `vmadot`
（VLEN=128、SEW=8 时选中的 MAC 单元是 2x2x4[x2]，而规范说硬件未实现的单元会触发非法
指令，因此 SEW=4 与 SEW=16 变体、以及 `e32, m1` 累加器，可以指出本簇实际实现的是哪个
单元），以及它的累加器是宿主栈数组，而能工作的内核只写入启动时给的那个缓冲区。

这两点现在都由探针本身回答了。宿主栈累加器正是 launch 时崩溃的原因：把 C 写进启动时
给定的缓冲区，launch 就能完成。随后规范的"偶 `vd`"规则又咬了一次——**C 占两个连续向量
寄存器**，因此在 VLEN=128 下一个用例需要 16 个 int32；第一个能跑的版本只留了一个寄存器的
量，这正是它的掩码里出现大于 1 的数值的原因。

一次启动跑完 32 个用例后，映射被测了出来，而且**不是**朴素那个：输入值 1 产生了 1、16、
17、32、33、66、70 这样的结果，说明**MAC 以 4 bit 通道消费操作数**，尽管配置请求的是
`e8`（字节 0x01 被读成半字节 (1,0)，0x10 读成 (0,1)）。这正是按规范文字写出的内核四个
输出全错的原因。现在解读映射需要的是"用可区分的逐位置数值做一次设计好的运行"，而不是
继续打通链路；同时如实保留一条：进程在打印完映射后仍报 `free(): invalid next size`，
因此映射有效，而它周围的分配纪律尚未定论。

随后两处改动把能定的都定下来了。探针的缓冲区改为页对齐映射而非 vector 存储，退出时的
分配器抱怨随之消失——这记为**隔离**而非诊断，因为究竟是运行时越界写还是跨过了分配器
边界仍未确定。另外，未动的那侧操作数现在按位置携带 1..16，于是 C 的数值能指出它与哪个
位置配对：每个 A 用例里都有一个 C 槽携带随 A 位置推移的小数值（2、5、7、9、11……），
而大常数（1496、2992）是多通道求和，并且常数在 A 位置 11 与 12 之间发生变化——副本结构
确实存在且不对称，与规范里"滑动打包"的说明一致。

完整置换仍未写成表，且在写成之前不报任何速率：把配对信号变成打包例程需要一次刻意设计
的求解（两个操作数各放单个 1、遍历 (p,q)、读回哪个 C 槽应答），而不是再读一遍这张表。

这次求解已经做了——256 个用例、A 在 p 位置与 B 在 q 位置各放单个 1、单次启动、干净
退出——而它的答案不是一个置换：256 个用例里只有 33 个有输出，单个用例最多点亮 12 个 C
槽，并且**只有 A 的前两个字节参与**（p = 0 与 1 能与所有 q 相乘，p ≥ 2 什么都不产生）。
一个输入 1 点亮多个累加器，与规范里"滑动打包"的措辞以及此前"4 bit 通道"的发现一致；而
两字节的操作数消耗如果成立，就意味着在 A100 上手写 vmadot 内核需要为每个权重字节付出
许多条指令——正好与厂商在那边达到的 9.0 与 5.8 GiB/s 相反。

这还不是结论：本次扫描只用了**一种**配置（`e8` 配 `e32, m2` 累加器）。`e4`、`e16` 与
不同 `vl` 的变体才能说明"操作数消耗很小"是这种配置的属性还是整个簇的属性。这里记录的
是 A100 自研内核路线的现状：一个有测量支撑的障碍，距离被判定只差几组配置运行。

### 该障碍已撤回：A 的每个字节都参与

配置变体已经跑完，而它们否证了上面那一段。改为"A 在 p 放单个 1、**B 全为 1**"（与配对
扫描问的是不同问题）后，两种满向量配置都显示 **A 的十六个位置全部有效**（`e8`：0–15；
`e16`：0–15），而 AVL=8 一行显示窗口随 `vl` 变小而收窄（0–7 去掉 6）。因此此前的稀疏是
**配对**的属性，而非操作数消耗的属性：两个操作数各只有一个 1 时，只有伙伴落在 16 字节
B 窗口内的那些 A 位置才能应答。

同时记录两条工具链事实：规范里的 SEW=4 配置在本汇编器上**根本无法请求**
（`vsetvli ..., e4, m1` 报 "illegal operands"，而立即数 AVL 形式是 `vsetivli` 而非
`vsetvli`），要触达
规范表里最小的 MAC 单元需要裸指令编码；另外编译失败过去会把**上一个**二进制留在 stage
——这就是某次扫描毫无输出、看起来像"静默结果"的原因，现在 `build.sh` 会在编译前删除两个
二进制。

A100 自研内核路线剩下的是：用足够宽的 B 窗口做一次配对求解、写出打包例程、再测 R=1/2/4
的速率与厂商 9.0 与 5.8 GiB/s 对比。

### 那次求解定下了操作数尺寸，并显示布局是广播式的

按上述做法执行——64 字节用例、A 跨两个寄存器、B 在第三个寄存器、两个操作数各放一个 1、
共 512 种组合——结果否证了加宽窗口所依据的假设，并定下了操作数尺寸：

- **A 只有一个寄存器，不是两个。** A 的 16..31 位置从不作答，因此在 VLEN=128、SEW=8
  下一条指令消耗 16 字节 A 与 16 字节 B——正是规范在这个向量长度下的 2x2x4 配 Copies=2。
- **操作数是广播式而非一对一映射。** 每个 A 位置几乎与每个 B 位置配对，而点亮的 C 槽
  只有很小一集合（`{0,2,6}`、`{2,6}`），不是每对一槽：一个字节被滑过多条 MAC 通道，
  这正是"滑动打包"的含义，也是按文字写出的打包会出错的原因。

通往打包还有两条具体路径：用已知 GEMM 对全 1 运行做拟合、比对候选布局；或者更短的一条
——反汇编板卡上 `libllama-bench-impl.so` 里厂商自己的 i8i4 内核，那才是真正以 9.0 GiB/s
喂这块硅的代码。在任一条落地前不报任何速率。

### 第二条路径给出了答案，并且把问题本身换掉了

内核不在 `libllama-bench-impl.so`，而在板卡的 `libggml-cpu.so.0.16.0` 里；该库未 strip，
导出 `spacemit_kernels::ime2::gemm_kernel_i8i4` 及其 `_m1`/`_m4` 叶子（派发器是按行数
阈值二选一的桩，正是内核探针从外部看到的规则）。反汇编解码路径的叶子：

```
c6850:  vsetvli t0,zero,e8,m1,tu,mu
c6854:  vl4r.v  v4,(s5)          # 四寄存器分段加载
c685c:  vsetvli t0,zero,e8,mf2,tu,mu
c6860:  vle8.v  v30,(s4)
c687c:  flw     ft0,0(s2)        # scale
c683a:  vfcvt.f.x.v v0,v0        # 在寄存器内反量化为浮点
c6908:  vfmacc.vf v2,ft0,v31     # 浮点乘累加
```

**整库里 `vmadot` 出现零次**，最罕见助记符列表里也没有任何标准 RVV 与标量集之外的
东西。`ime2` 这个名字描述的是构建配置与目标核，而不是某条矩阵指令：厂商在智算簇上达到
9.0 GiB/s，靠的是手写 RVV——按 64 字节分段加载 4 bit 权重、在寄存器内转换、再用
`vfmacc` 累加。

这抹掉了前三轮一直在追的那个障碍，并指出了该做什么：按厂商的形状写一个 RVV gemv
（分段 4 bit 加载、寄存器内反量化、`vfmacc` 累加、每个权重读取服务四行），与标量参照
对拍，再与那 9.0 GiB/s 对比。IME 布局那条工作已不在关键路径上。
