# Spine-Runtime 项目

厂商针对智算核给出的编程模型，也是唯一有文档的提交入口。`libspert` 是预编译的；
API 与调度模型是公开的。

## 固定来源

| 字段 | 取值 |
|---|---|
| 上游 | `https://github.com/spacemit-com/spine-runtime.git` |
| ref | `main` |
| 提交 | `b3ff5182de116613b6db72b0f43064554ac3d42d` |
| 许可证 | MIT |
| 检出 | `src/spine-runtime` |
| SDK 包 | `spine-runtime.riscv64.0.6.2.tar.gz`，`libspert.so.0.6.2` |

模型是 Tile-SPMD：`Stream` 持有后端授予的计算核，`Grid` 把工作切成 tile，每个 tile
从 `Context` 读取自己的坐标。`backend_info()` 报告实际获得的核心数、共享缓冲大小、
向量长度与架构 id。`spacemit-k3` 后端面向智算核 8-15，每核 384 KiB 缓冲；
`spacemit-k3-x100` 是 X100 核上的兼容模式，`generic/qemu` 仅供功能验证。

## A100 ISA 标志与我们提交的内核

`scripts/build.sh` 为智算簇编译这两个二进制（它们的内核在簇上执行）：默认是
`-march=rv64imafdcv_zicsr_zifencei_zba_zbb_zbs_xsmtvdotii -mtune=spacemit-a100`，
即显式给出 A100 ISA 与厂商调度模型，而不用那把"打包式"的 `-mcpu` 开关。可用
`SPERT_A100_FLAGS` 覆盖。

选定它的矩阵如下，每个构建跑 5 次 `a100_bandwidth 64`（每次含 4 个变体，只有 4 个都
完成才计为成功一次）：

| 构建 | 完成次数 |
|---|---|
| 纯 `rv64gc` | 4/5 |
| 只用 `-mtune=spacemit-a100` | 3/5 |
| `-march` 不带向量 | 3/5 |
| `-march` 带向量 | 4/5 |
| `-march` 带向量与 `_xsmtvdotii` | 3/5 |
| `-mcpu=spacemit-a100` | **0/5** |

两个发现，以及一处对本文件早先说法的更正。更正：该项第一次测量（3 次）写成"这个标志
决定它们能否运行"；做到 5 次后真相更窄——只有打包式的 `-mcpu=spacemit-a100` 是确定性
失败，其余任何子集的表现都与纯构建无异。这也意味着工具**本身就在随机失败**：连纯构建
也大约五次里失败一次，这是工具或它对运行时的用法里的未解缺陷，而不是任何 ISA 选项的
问题，也正是默认值现在避开那把每次都失败的开关的原因。

内存天花板不受这些影响：纯构建与向量构建在纯流式上一致为 24.6 GiB/s，在解码路径自己
那条瓦片走法上接近 23 GiB/s，因此天花板是总线而不是指令组合。标量半字节解包在所有
构建里都读 2.7 GiB/s；要回答 4 bit 格式本身能否喂满总线，仍需手写向量化解包。

## 一次读取服务 R 行

`a100_bandwidth` 现在还带有 `gemvR1`、`gemvR4`、`gemvR8`：对打包的 4 bit 权重走一遍，
分别服务 1、4、8 行激活，每个结果都与主机侧参照比对。在 1.5 GiB 工作集下实测：

| 变体 | MiB/s |
|---|---|
| `gemvR1` | 2,610 |
| `gemvR4` | 2,481 |
| `gemvR8` | 2,547 |

速率随 R 增长保持不变，而厂商自己的内核会掉速：解码运行中它的单行 `i8i4` 内核流式
9.0 GiB/s、四行内核 5.8 GiB/s。这正是本仓库能为 LLM 那条线回答的问题形状——批处理因
重新分组而损失的 25 % 至 30 % 是厂商内核结构的属性，而不是内存路径的属性——前提是
说清本内核是标量的：它只证明 R 不改变*它自己*的速率，并不证明它达到了厂商的速率。
向量化解包版本是下一步，而现在的构建已经能接受可运行的 A100 ISA。

## 不要让编译器去向量化这些内核

想用 `-O3 -mrvv-vector-bits=zvl` 走捷径，结果是**每个变体都算错**，包括最简单的
`word` 与 `byte` 循环——只因为每个变体都要与主机侧参照比对才被发现。`zvl` 会从
`-march` 字符串取向量长度，而厂商扩展集带着 `zvl1024b`，智算核实际是 `vlen=128`，
于是编译器面向一台并不存在的机器生成代码；GCC 15 只接受 `scalable` 或 `zvl`，
因此也无法直接写 128。这个构建也没有更快：`word` 从
24,759 掉到 9,741 MiB/s。回答那个问题只剩手写内核一条路，而且它必须自带校验和。

## 手写内核同样达不到厂商的速率

解包部分的手写内核现在有了（`pack4v`，RVV 内建函数，带主机侧校验），它把问题回答到了
另一边：

| 变体 | MiB/s |
|---|---|
| `word`（纯流式） | 24,168 |
| `tiled` | 23,233 |
| `pack4`（标量解包） | 2,728 |
| `pack4v`（RVV 解包） | 2,536 |

向量解包**比标量循环还慢**，而两者都低于厂商单行内核（9.0 GiB/s）3.3 至 3.6 倍。厂商的
优势几乎可以确定来自 IME2 指令族：工具链能生成它，但本工作区没有它的编程模型文档。
因此结构性的发现——批处理损失的 25 % 至 30 % 源于厂商内核结构而非内存路径——依然成立，
但要把这笔收益兑现，需要 IME2 文档，而不是在这里继续测量。另有两条旁证记录在案：逐通道
归约的版本更快但结果错误（失配量恰好等于一个 pass 的半字节和），以及工具现在在失配时
同时打印期望值与实际值，而不只是 "mismatch"。

## IME 文档是存在的，而且这些指令在 X100 核上可运行

上面那段写在查阅规范之前。规范确实存在——`spacemit-com/riscv-ime-extension-spec`
公布了指令（`vmadot`、`vmadot1`/`2`/`3`/`n`、`vmadotu`/`su`/`us`，以及浮点的
`vfmadot*` 族）、数据类型（int4/int8/int16、fp4/fp8/fp16/bf16）、由 `vl*SEW` 决定的
MAC 单元，以及编程模型（复用 RVV 寄存器、不新增状态、VLEN 128–4096、SEW 4/8/16、
LMUL ≤ 1）——其 `example/vmadot-gemm-demo.c` 是一个自带自检的 4x8x4 int8 GEMM。

本地实测：该示例用 `-march=rv64gcv_xsmtvdotii` 编译（纯 `-march=rv64gcv` 会拒绝该
助记符），在 **X100 核**上运行并打印 `Test successful. CRef equal to C.`，`taskset -c 0`
同样通过。同形状的循环实测：标量 786 Mmac/s，`vmadot` 18,286 Mmac/s——23 倍——但
**结果不同**，因为 VLEN=128、SEW=8 时 MAC 单元是 2x2x4[x2]，操作数必须按示例里
`Gemm_packB` 的方式打包。

所以“IME2 无文档、只能经智算簇运行时到达”这句话对本板不成立：指令集是公开的，并且作为
普通用户态代码在 Linux 簇上执行。自己写多行内核这件事重新开放，前提是先写好打包例程并
通过自检。

## 这样的内核实测到多少

用 demo 的形状、B 操作数只打包一次，然后从大缓冲里流式读取，累加器在整个循环里常驻向量
寄存器；**单个** X100 核、`taskset -c 0`：

| 权重缓冲 | 校验 | 速率 |
|---|---|---|
| 256 MiB | ok | 8,029 MiB/s |
| 1 GiB | ok | 7,832 MiB/s |

与其他流式实现对比：我们的标量解包在全部八个智算核上是 2.7 GiB/s、RVV 解包 2.5 GiB/s，
厂商的单行内核在智算簇上每内核 9.0 GiB/s。也就是说单个 X100 核已达厂商单内核速率的
15 % 以内；八个这样的核将索取约 61 GiB/s，而天花板是 24.6 GiB/s；MAC 单元本身就是
"每个权重块配一个四行激活块"（正是厂商在重组批时丢掉 25 % 至 30 % 的那个结构）；而且
这一切都是 cpu0-7 上的普通线程，`taskset`、按进程记账、perf 与 eBPF 采集器全都适用。

另有一条记录：X100 核上 `csrr vlenb` 读出 32 字节，即 **VLEN=256**，而智算簇后端报告
128——两簇不可互换，这也是为 VLEN=256 编写的 demo 能在本板通过的原因。

尚未完成：多核版本、解码形状的 K，以及任何端到端 token 速率。

## A100 需要自己的布局工作，而且这部分靠测而不是靠读

解码工作跑在智算簇上，所以真正要紧的是 A100 的内核——而 A100 的 **VLEN=128**、X100
是 256。规范里的 `Copies` 规则让这个差别成为结构性的：
`Copies = (sqrt(VLEN/64) is an integer) ? 1 : 2`，于是 VLEN=128 得 Copies=2、
VLEN=256 得 Copies=1，随之而来的操作数布局也不同
（VLEN=128、SEW=8 选 2x2x4 MAC 单元；VLEN=256 则是 4x4x8）。

两条结论按“记录而非假设”处理：本板验证正确的厂商 demo 是 **VLEN=256** 内核，其布局
不能直接搬用；只按规范文字写出的内核——A 为 `Copies*(M,K)` 行主序、B 为 `Copies*(K,N)`
列主序、每条 `vmadot` 出 2x2 输出且 K=8——能在 A100 上编译运行，但**复现不了参照**
（四个输出全部不符）。规范的布局图是图片，其整数伪代码又把 C 当作 (M,N) 矩阵却索引
`i*K + j`，在 M ≠ N 时不可能成立。

出路是用一个布局探针把置换关系**测出来**：通过 `spert` 提交到 8-15 核，与本工作区当初
测“tracepoint 程序按 tracepoint 挂载而非按 CPU”是同一方法——源码是假设，探针是事实。
随后是打包例程，然后是 R=1/2/4 下相对厂商 9.0 与 5.8 GiB/s 的速率。

### 在启动在飞时异常退出会把运行时一起带走

该探针的两次尝试都落在同一处：

| 事件 | 症状 | 恢复方式 |
|---|---|---|
| 探针运行中被 `pkill` | 之后所有 stream 被拒（`reason=stream-refused`），`a100_probe` 无输出，TCM 8/8 空闲 | 重启 |
| 探针段错误 | 同样症状，连刚才能正常工作的 `a100_bandwidth 64` 也返回零结果 | 重启 |

重启后簇立刻恢复健康（`a100_probe` 报 `kernels=ok mismatches=0 us_per_launch=31.2`，
`a100_bandwidth 64` 报 `word 24,881 MiB/s`），因此被破坏的是运行时侧状态而非硬件。由此
得到适用于本工作区所有 harness 的规则：不要 kill 正在提交启动的进程；提交方段错误要同等
对待；任何异常退出之后，都要先重新确认簇健康再相信下一次测量。探针本身分三个阶段尚未
完成：先是空转（八核 stream 上用单 tile 网格、且没检查 `future.valid()`）；随后段错误
且诊断信息被 stdout 缓冲吞掉；再到后来改成无缓冲 stderr + 单次启动跑完 32 个用例，仍在
sync 处段错误——但输出把故障定位到 launch/sync 边界，而且**这次没有污染运行时**
（紧接着 `a100_probe` 与 `a100_bandwidth` 都正常）。因此“段错误会毒化运行时”的说法
收窄为：kill 两次都毒化了，段错误毒化过一次；可靠规则是不要在启动在飞时 kill，并且任何
异常退出之后都先核对簇健康、而不是假定结果。

与这里所有能工作的内核相比，本探针有两处不同，直接指向下一步实验：它执行 `vmadot`
（VLEN=128、SEW=8 时选中的 MAC 单元是 2x2x4[x2]，而规范说硬件未实现的单元会触发非法
指令，因此 SEW=4 与 SEW=16 变体、以及 `e32, m1` 累加器，可以指出本簇实际实现的是哪个
单元），以及它的累加器是宿主栈数组，而能工作的内核只写入启动时给的那个缓冲区。

这两点现在都由探针本身回答了。宿主栈累加器正是 launch 时崩溃的原因：把 C 写进启动时
给定的缓冲区，launch 就能完成。随后规范的"偶 `vd`"规则又咬了一次——**C 占两个连续向量
寄存器**，因此在 VLEN=128 下一个用例需要 16 个 int32；第一个能跑的版本只留了一个寄存器的
量，这正是它的掩码里出现大于 1 的数值的原因。

一次启动跑完 32 个用例后，映射被测了出来，而且**不是**朴素那个：输入值 1 产生了 1、16、
17、32、33、66、70 这样的结果，说明**MAC 以 4 bit 通道消费操作数**，尽管配置请求的是
`e8`（字节 0x01 被读成半字节 (1,0)，0x10 读成 (0,1)）。这正是按规范文字写出的内核四个
输出全错的原因。现在解读映射需要的是"用可区分的逐位置数值做一次设计好的运行"，而不是
继续打通链路；同时如实保留一条：进程在打印完映射后仍报 `free(): invalid next size`，
因此映射有效，而它周围的分配纪律尚未定论。

随后两处改动把能定的都定下来了。探针的缓冲区改为页对齐映射而非 vector 存储，退出时的
分配器抱怨随之消失——这记为**隔离**而非诊断，因为究竟是运行时越界写还是跨过了分配器
边界仍未确定。另外，未动的那侧操作数现在按位置携带 1..16，于是 C 的数值能指出它与哪个
位置配对：每个 A 用例里都有一个 C 槽携带随 A 位置推移的小数值（2、5、7、9、11……），
而大常数（1496、2992）是多通道求和，并且常数在 A 位置 11 与 12 之间发生变化——副本结构
确实存在且不对称，与规范里"滑动打包"的说明一致。

完整置换仍未写成表，且在写成之前不报任何速率：把配对信号变成打包例程需要一次刻意设计
的求解（两个操作数各放单个 1、遍历 (p,q)、读回哪个 C 槽应答），而不是再读一遍这张表。

这次求解已经做了——256 个用例、A 在 p 位置与 B 在 q 位置各放单个 1、单次启动、干净
退出——而它的答案不是一个置换：256 个用例里只有 33 个有输出，单个用例最多点亮 12 个 C
槽，并且**只有 A 的前两个字节参与**（p = 0 与 1 能与所有 q 相乘，p ≥ 2 什么都不产生）。
一个输入 1 点亮多个累加器，与规范里"滑动打包"的措辞以及此前"4 bit 通道"的发现一致；而
两字节的操作数消耗如果成立，就意味着在 A100 上手写 vmadot 内核需要为每个权重字节付出
许多条指令——正好与厂商在那边达到的 9.0 与 5.8 GiB/s 相反。

这还不是结论：本次扫描只用了**一种**配置（`e8` 配 `e32, m2` 累加器）。`e4`、`e16` 与
不同 `vl` 的变体才能说明"操作数消耗很小"是这种配置的属性还是整个簇的属性。这里记录的
是 A100 自研内核路线的现状：一个有测量支撑的障碍，距离被判定只差几组配置运行。

### 该障碍已撤回：A 的每个字节都参与

配置变体已经跑完，而它们否证了上面那一段。改为"A 在 p 放单个 1、**B 全为 1**"（与配对
扫描问的是不同问题）后，两种满向量配置都显示 **A 的十六个位置全部有效**（`e8`：0–15；
`e16`：0–15），而 AVL=8 一行显示窗口随 `vl` 变小而收窄（0–7 去掉 6）。因此此前的稀疏是
**配对**的属性，而非操作数消耗的属性：两个操作数各只有一个 1 时，只有伙伴落在 16 字节
B 窗口内的那些 A 位置才能应答。

同时记录两条工具链事实：规范里的 SEW=4 配置在本汇编器上**根本无法请求**
（`vsetvli ..., e4, m1` 报 "illegal operands"，而立即数 AVL 形式是 `vsetivli` 而非
`vsetvli`），要触达
规范表里最小的 MAC 单元需要裸指令编码；另外编译失败过去会把**上一个**二进制留在 stage
——这就是某次扫描毫无输出、看起来像"静默结果"的原因，现在 `build.sh` 会在编译前删除两个
二进制。

A100 自研内核路线剩下的是：用足够宽的 B 窗口做一次配对求解、写出打包例程、再测 R=1/2/4
的速率与厂商 9.0 与 5.8 GiB/s 对比。

### 那次求解定下了操作数尺寸，并显示布局是广播式的

按上述做法执行——64 字节用例、A 跨两个寄存器、B 在第三个寄存器、两个操作数各放一个 1、
共 512 种组合——结果否证了加宽窗口所依据的假设，并定下了操作数尺寸：

- **A 只有一个寄存器，不是两个。** A 的 16..31 位置从不作答，因此在 VLEN=128、SEW=8
  下一条指令消耗 16 字节 A 与 16 字节 B——正是规范在这个向量长度下的 2x2x4 配 Copies=2。
- **操作数是广播式而非一对一映射。** 每个 A 位置几乎与每个 B 位置配对，而点亮的 C 槽
  只有很小一集合（`{0,2,6}`、`{2,6}`），不是每对一槽：一个字节被滑过多条 MAC 通道，
  这正是"滑动打包"的含义，也是按文字写出的打包会出错的原因。

通往打包还有两条具体路径：用已知 GEMM 对全 1 运行做拟合、比对候选布局；或者更短的一条
——反汇编板卡上 `libllama-bench-impl.so` 里厂商自己的 i8i4 内核，那才是真正以 9.0 GiB/s
喂这块硅的代码。在任一条落地前不报任何速率。

### 第二条路径给出了答案，并且把问题本身换掉了

内核不在 `libllama-bench-impl.so`，而在板卡的 `libggml-cpu.so.0.16.0` 里；该库未 strip，
导出 `spacemit_kernels::ime2::gemm_kernel_i8i4` 及其 `_m1`/`_m4` 叶子（派发器是按行数
阈值二选一的桩，正是内核探针从外部看到的规则）。反汇编解码路径的叶子：

```
c6850:  vsetvli t0,zero,e8,m1,tu,mu
c6854:  vl4r.v  v4,(s5)          # 四寄存器分段加载
c685c:  vsetvli t0,zero,e8,mf2,tu,mu
c6860:  vle8.v  v30,(s4)
c687c:  flw     ft0,0(s2)        # scale
c683a:  vfcvt.f.x.v v0,v0        # 在寄存器内反量化为浮点
c6908:  vfmacc.vf v2,ft0,v31     # 浮点乘累加
```

**整库里 `vmadot` 出现零次**，最罕见助记符列表里也没有任何标准 RVV 与标量集之外的
东西。`ime2` 这个名字描述的是构建配置与目标核，而不是某条矩阵指令：厂商在智算簇上达到
9.0 GiB/s，靠的是手写 RVV——按 64 字节分段加载 4 bit 权重、在寄存器内转换、再用
`vfmacc` 累加。

这抹掉了前三轮一直在追的那个障碍，并指出了该做什么：按厂商的形状写一个 RVV gemv
（分段 4 bit 加载、寄存器内反量化、`vfmacc` 累加、每个权重读取服务四行），与标量参照
对拍，再与那 9.0 GiB/s 对比。IME 布局那条工作已不在关键路径上。

### RVV gemv 已写出、已对拍，但落后 4.5 倍

`a100_bandwidth` 现在带有 `rvvgemv`：按厂商形状写成的标准 RVV——4 bit 块以 16 字节流式
读取、每块乘以其 scale 后累加，并与主机侧参照核对。它需要一处修复值得记录：u32 的
**归约**会把 16 条通道相加，因此 drain 窗口必须让 16 条通道的总和仍在 u32 内，而不是单条
通道；每 1,024 块归约会溢出（被参照抓到），每 64 块则不会。

在 1536 MiB 工作集下，逐行都有校验：

| 变体 | MiB/s |
|---|---|
| `word`（纯流式） | 24,166 |
| `tiled` | 22,357 |
| `gemvR1`/`gemvR4`/`gemvR8`（一次读取服务 1/4/8 行） | 2,691 / 2,500 / 2,594 |
| `pack4`（标量解包） | 2,730 |
| `pack4v`（RVV 解包） | 2,145 |
| `rvvgemv`（厂商形状的 RVV） | 2,012 |
| 厂商 `i8i4_m1`（内核探针） | 9,000 |

因此自研内核这条路**技术上是通的**——厂商用的是普通 RVV，我们的内核能在簇上跑通并通过
校验——但它比必须超越的那个内核**慢 4.5 倍**，而这里写出的任何变体都没超过 2,700 MiB/s。
要抹平差距就得复刻一个手工调优的循环（`vl4r.v` 分段加载、寄存器内浮点转换、`vfmacc`
流水与他们的调度），那是一个重实现项目，而收益上限正是厂商四行分块丢掉的那 25 % 至 30 %。
按"已测量"记录，选择保留而不替他做。

### 更细致的检查更正了上面这段：解码内核执行的是我们无法汇编的指令族

> 当晚即被推翻：这些族是公开的 `smt.*`，本工具链可以汇编。见文末的更正。

上面说厂商用的是"普通 RVV"。把 objdump 无法解码的指令（渲染为 `.insn 4, 0x...`，
助记符检索看不到）统计出来后，这个说法需要更正：库中共有 **494 条**此类指令，按 `funct7`
分成若干族：

| funct7 | 库中数量 | 我们的工具链 |
|---|---|---|
| 0x71 | 176 | 可汇编：这就是文档化的 `smt.vmadot` 族 |
| 0x33 | 200 | 无助记符、无解码器 |
| 0x66 | 32 | 无助记符、无解码器 |
| 0x6B | 20 | 无助记符、无解码器 |
| 0x21 / 0x61 / 0x6A / 0x79 / 0x7A / 0x7B | 14 / 8 / 12 / 16 / 8 / 8 | 无助记符、无解码器 |

而解码叶子 `ime2::gemm_kernel_i8i4_m1` 里 **0x71 族一条都没有**，另五族共 40 条
（0x66×12、0x33×10、0x6B×8、0x21×6、0x6A×4）。也就是说，产出 9.0 GiB/s 的那个内核

### 一轮公开资料核查：解码内核用的指令族没有公开

> 当晚即被推翻：厂商自己的 `docs-ai` 架构章节就写了这些指令，本工具链既能反汇编也能
> 汇编。见文末的更正。

按顺序核对了：

| 来源 | 结果 |
|---|---|
| IME 规范（26 行指令表、v1.0 正式版 PDF） | 只列出 `vmadot*`（funct7 0x70/0x71）与 `vfmadot*`（0x74），**没有**解码内核那五族中的任何一族 |

因此产出 9.0 GiB/s 的内核所用的指令族**不在公开资料中**——不在规范里、不在任何已发布

那 4.5 倍：这些指令在本工作区无法汇编，拿到它们（或支持它们的汇编器）是人的动作。

**还有一族公开指令没试过**：`sf.vqmacc.2x8x2` 与 `sf.vqmacc.4x8x4` 及其 `u`/`su`/`us`
形式——opcode 0x5b 的四比特量化矩阵乘，公开、可用
`-march=rv64gcv_xsfvqmaccdod_xsfvqmaccqoq` 汇编，形状恰好对应厂商内核名字里的行数。
它是本工作区里唯一为同一用途设计的指令族，因此在关闭这条路线之前，它是唯一还值得跑的
自研内核实验。

### 该族在 A100 上触发陷阱，这条路线就此关闭

`a100_bandwidth --sfqmac` 会在每个核上启动一个内核，只执行待验证的那条指令，累加器放在
启动缓冲区，其余不作任何假设：

| 指令 | 结果 |
|---|---|
| `sf.vqmacc.4x8x4 v28, v0, v1` | launch 永不返回——没有 `synced`、没有数值，进程退出；簇保持健康（`a100_probe`：`kernels=ok mismatches=0 us_per_launch=29.2`） |
| `vmadot v28, v0, v1`（同一路径，只换一条指令） | 正常完成，每个核返回 `[16 0 0 0 0 0 0 0]` |

对照正是让它成为"关于指令本身"的结论：启动路径、缓冲区、grid、读取代码完全相同，一条
指令能同步、另一条永不返回。这就是 AI 核上的非法指令——binutils 能编码该扩展，硅片没有
实现它，而运行时并不把这陷阱作为错误上报。

至此这块簇上的每个公开选项都已测量：

| 指令族 | A100 上 | 我们最好 | 厂商 |
|---|---|---|---|
| `smt.vmadot*`（规范，funct7 0x71） | 可运行 | 2,012–2,730 MiB/s | 9,000（`i8i4_m1`） |
| `sf.vqmacc.*`（0x5b） | **陷阱** | — | — |
| 普通 RVV | 可运行 | 2,730 MiB/s（`pack4`） | — |
| 解码内核自己的族（0x21/0x33/0x66/0x6A/0x6B） | 可运行（那是他们的代码） | **公开的 `smt.*`，在此可按字节一致地汇编** | 9,000 |

因此为这件事设计的 `sf.vqmacc` 族在硅片上触发陷阱，而这里写的 RVV 内核落后 4.5 倍。
本节记录中的第三个说法——达到 9,000 MiB/s 的那族没有公开汇编器——已在下面被推翻。
A100 并行解码的指引保持不变（np=4 为拐点、取 lockstep 而非服务形态、四行分块属厂商）。

### 更正：解码内核用的族是公开的 `smt.*`，本工具链可以汇编

上面两节都错了，且错因各自独立；而修正比错误本身更有价值。

**反汇编器被要求不要解码它们。** 本工具链的 RISC-V 反汇编器会用"架构字符串"对每条指令
做门控，而这个字符串取自被反汇编文件的 ELF 属性。厂商库声明的是
`Tag_RISCV_arch: "rv64i2p1_..._zvl128b1p0"`，没有任何厂商扩展，于是它的每一条厂商指令
都打印成 `.insn 4, 0x...`。`-M max`（"disassemble without checking architecture
string"）解除门控后，未解码字数降到 **0**：

| 助记符 | 在 `libggml-cpu.so.0.16.0` 中的条数 |
|---|---|
| `smt.vpack.vv` | 150 |
| `smt.vmadot` | 144 |
| `smt.vupack.vv` | 50 |
| `smt.vmadotsu.hp` | 48 |
| `smt.vmadotu.hp` | 32 |
| `smt.vmadotsu` | 28 |
| `smt.vmadot.hp` | 16 |
| `smt.vnpack4.vv` | 14 |
| `smt.vmadotu` | 12 |

494 正是先前被记为"无法解码"的数量，也就是说那张按 `funct7` 划分的"五族"表，就是这一套
公开指令集，只是没有被读出来。

**汇编测试用错了操作数形式。** `.hp` 形式是五个操作数再加数据类型后缀
（`vd, vs1, vs2, v0/v1, imm3, i4|i8`），打包形式是四个（`vd, vs1, vs2, imm2`）；
先前的检查只写了三个。按厂商自己反汇编打印出的形式写，本工具链可以**逐字节**复现厂商的
编码：

| 厂商解码叶子里的字 | 本工具链 |
|---|---|
| `d645082b` `smt.vmadotsu.hp v16,v10,v4,v1,0,i4` | 一致 |
| `cc44082b` `smt.vmadotu.hp v16,v8,v4,v0,0,i4` | 一致 |
| `67281c2b` `smt.vpack.vv v24,v16,v18,1` | 一致 |
| `4231b42b` `smt.vnpack4.vv v8,v3,v3,3` | 一致 |

还有第三个原因，它本该在第一轮核查开始前就拦下那次结论：厂商公开的 `docs-ai` 记录了这一整族，
而且自 2026-09-17 起就克隆在本工作区里。`en/architecture/ime_extension.md` 是
`Zvvm_spacemit` 0.6 版，"Status: Public Release"，2026-04-13；第 5.4 章把
`smt.vmadot.hp*` 定义为分块量化路径 `C <- (A x B) x S + C`（FP16/BF16 缩放），
第 8.4 章给出正式编码，其字段手工代入即可复现 `0xd645082b`，而汇编器强制的那条寄存器
约束（`v0`/`v1`）正是规范原文。

于是厂商解码内核可以按其真实面目读懂了：`vnpack4` 打包 4 bit 权重，
`vmadotsu.hp`/`vmadotu.hp` 把 Int4 与 Int8 的 tile 乘上 FP16 分块缩放并累加到 FP16，
`vpack` 交错累加器。4.5 倍差距现在是一项"指令已到手"的重实现任务，而不是一条等厂商材料的
路线。`sf.vqmacc.*` 在这块硅片上仍然触发陷阱，继续排除在外。下一步测量见下节。

### 厂商自己的指令族在 A100 上可以运行

`a100_bandwidth --smthp` 每核启动一个内核，全部工作只有一条
`smt.vmadotsu.hp v24,v16,v16,v0,0,i4`，操作数与累加器都在 launch 缓冲区里。输入取齐次值，
使结果与 tile 跨度无关：两个操作数的每个 nibble 都是 1，缩放寄存器每个 lane 都是 FP16
1.0，于是每个输出 lane 都是 32 个 1×1 再乘 1.0 = 32.0 = `0x5000`。

| 内核 | 每核 |
|---|---|
| `--smthpctl` 对照：同样的 launch、同样的缓冲区，内核里没有任何矩阵指令 | 各核写入并读回自己的 tile id |
| `--smthp` | **八个核的全部 64 个累加器 lane 都是 `0x5000`** |

也就是说，产出 9,000 MiB/s 的那个解码内核所用的指令族，在这块硅片上确实可以执行，并且返回
公开语义预测的值，写满整个 tile，并且指令之后核心仍能正常写内存。

### 向量长度此前被用错了单位

`spert.hpp` 里 `BackendInfo::vlen` 的单位写明是**字节**，而本项目早前的轮次把它的 `128`
当成了位，并据此推导"16 字节向量寄存器"。在智算核上运行的内核里读 `csrr vlenb`，八个核
全部返回 **128**；厂商自己的指令集文档也把该族的 A100 固定为 `VLEN = 1024 bits`、
`lambda = 8`、`MUL_C = 1`、`SEW = 16`。因此一个寄存器是 128 字节，8×32×8 Int4 每个操作数
正好一个寄存器，8×8 累加器是一个 64 个 FP16 lane 的寄存器。X100 后端报 `vlen=32`
（32 字节 = 256 位，A60 级核心）是单位问题上的第二重佐证。本文件中所有把 A100 的 tile 说成
"两个 16 字节寄存器"或"跨寄存器广播"的表述一并撤回；上面那个 64 lane 的结果才是该几何真正
产生的东西。

`--smthpctl` 不是装饰：这个探针的第一版报出的散乱结果看上去像是指令本身的性质，而对照内核
完全没有矩阵指令却出现同样的散乱。由此依次暴露出三个探针缺陷——128 字节的向量存储写在只按
256 字节开窗的缓冲区上，以及两次内联汇编的输出寄存器与输入指针寄存器别名（一次把存储地址
变成 128，一次把 tile id 写成 `0x0080`）。本项目这种探针风格下的任何"每核"数字，现在都必须
先通过一次同形状、每核写入自身标识并读回的对照 launch：`a100_probe` 的 `out[tile]` 约定与
布局掩码通过，`--sfqmac` 对照里那行"每核"记录被重新标为未验证——它的结论（该族永不 sync）
不受影响。

### 厂商自己的形状能跑到 22.7 GiB/s，而厂商那个内核是 9.0

`a100_bandwidth` 现在把这个形状做成了一个变体：每 128 字节权重寄存器配一条
`smt.vmadotsu.hp`，再加一次 16 字节的八列 FP16 缩放加载——每条指令 144 字节流量，与厂商
`i8i4_m1` 入口被计费的口径一致（18 字节/32 权重/列，正是 9.0 GiB/s 那个数字的算法）。加载
部分做精确校验（每个权重寄存器异或进 16 个 lane，宿主端复现同一异或）；指令本身的算术由上面
的 `--smthp` 校验。

| 内核 | 64 MiB | 256 MiB |
|---|---|---|
| `word`（朴素流式，屋顶） | 25,176 | 24,623 |
| `tiled`（解码路径自己的走法） | 22,710 | 23,475 |
| `smthp`（厂商形状） | **22,679** | **22,670** |
| `smthpnd`（同样的循环，去掉矩阵指令） | 22,678 | 21,525 |
| `pack4`（标量解包） | 2,957 | 2,669 |
| `gemvR1`（一次读取服务一行） | 2,714 | 2,570 |
| `rvvgemv`（我们的 RVV gemv） | 2,094 | 2,008 |
| 厂商 `i8i4_m1`（早前轮次的内核探针） | 9,000 | — |

单位均为 MiB/s，计费口径同为"数据 + 缩放"。由此可得三点：在这个粒度上矩阵指令是免费的
（`smthp` 与 `smthpnd` 在噪声内一致，且都贴着 `tiled` 走法）；厂商形状的自研内核流式速率是
厂商单行内核的 2.5 倍、我们 RVV 最好成绩的 8–11 倍；而单序列解码在总量上**已经在这个屋顶
上**——每 token 1,465–1,475 MiB、14.0–14.4 t/s，即 21.1 GiB/s，对比此处实测的 22.7。
所以厂商的 9.0 GiB/s 是"单个内核"的数字，不是系统的天花板。

真正没到屋顶的是多行场景：np=4 时每 token 总量 402 MiB、总线占用 66.9 %，跑的是厂商四行
内核（早前测得 5.8 GiB/s）。按本次实测的流式速率，402 MiB/token 对应约 56 t/s 总量，而今天
是 41.0——这就是下一个实验。

关于工装本身还有一个必须记下的问题：提交进程会在退出时**偶发**段错误，而且是在全部工作完成、
所有校验都通过之后——本版如此，加入矩阵内核之前的版本也如此，去掉矩阵指令的对照同样如此，
`stdbuf -o0` 也不改变它。因此本项目的验收口径是：所有 `RESULT` 行齐全、全部 `checksum=ok`、
前后 `a100_probe` 健康；在这个缺陷被定位之前，进程退出码不是可用的成功信号。

### 解码内核是源码，不是黑盒

`spacemit_kernels::ime2::gemm_kernel_i8i4_m1` 不只在预编译库里，它就在我们固定的这个 fork 里：
`projects/llama.cpp/src/llama.cpp` 的 `ggml/src/ggml-cpu/spacemit/ime2_kernels.cpp`，
由 `gemm_kernel_i8i4` 分派——`count_m >= 4` 走 `_m4`，其余走 `_m1`。它自己的注释写明了两种格式：

| 侧 | 每个 k 块 | 字节 |
|---|---|---|
| A（激活，1 行，int8） | `fp32 scale | int16 asum | 32 x int8` | 38 |
| B（权重，32 列，int4） | `32 x fp16 scale | 32 columns x 16 bytes` | 576 |

而它的内层循环每个 k 块是：`vl4r.v`（512 字节权重）、`vle8.v`（64 字节缩放）、`vle8.v`
（32 字节激活）、两次 `vnpack4.vv`、八条 MAC（`vmadotsu.hp` / `vmadotu.hp`）、三次
`vpack.vv`、`vfwmul.vv`、`vfmacc.vf`——约二十几条向量指令处理 614 字节，累加器是 fp32 的
`v2`。

由此得到两点：上面测的那一族就是它跑的族，所以 9.0 与 22.7 GiB/s 之间的 2.4 倍既不是"指令
有没有"，也不是格式或内存通路；同时探针的字节计费对它是对的（每列每块 18 字节正是上表 B 侧）。
剩下的原因是循环本身而不是调用粒度，而且这是实测而非推断：内核里的普查
（`projects/llama.cpp` 的 patches/0001-ime2-call-shape-census.patch）显示每次
`i8i4_m1` 调用都是完整的 32 列分组、平均 71.35 个 k 块——每次调用搬运约 40 KiB 权重，
"调用太小"被否掉。每个 k 块它要发出约二十几条向量指令处理 614 字节，其中八条是 hp-MAC
打到四个累加器，再经三次打包与两次转换进 fp32 FMA；而其中五条只依赖本次调用的 A 侧求和，
却每轮重算。把这五条提出循环是第一个单变量候选，而验证它的构建回路已经存在：
`projects/llama.cpp/scripts/build.sh` 增量重建 stage 约十秒，stage 里的库在板上自带的
`llama-bench` 下测出 104.45 PP32 / 14.56 TG16，与厂商库在四倍形状下的 104.92 / 13.96 一致。
